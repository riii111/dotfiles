# Markdownの検査と整形

日本語の文章とSKILLの参照を検査し、文の区切りとMarkdownの書式を整える。

## 検査する観点

- **1行に1文を書く**
  - 理由：AIは複数の決まりを1行にまとめがち。
    ソースと差分を追いにくくなる。
    補足を同じ行に残すかどうかは機械的に判定できないため、例外を設けない。
  - 基準：日本語を含む行に2文以上ある。
    脚注の定義は本文から外した1つの補足なので対象外とする。

- **1文を長くしない**
  - 理由：AIは条件・理由・操作を1文につなげがち。
    読み終えるまで多くの情報を覚えておく必要があり、どの条件がどの操作にかかるか分かりにくい。
  - 基準：日本語を含む文が100字を超える。

- **括弧に説明を詰め込まない**
  - 理由：AIは条件や例外を括弧に押し込みがち。
    補足が長いと本文との往復が増え、主張や操作の流れを追いにくい。
  - 基準：日本語を含む括弧内が40字を超える。

- **冗長な表現を減らす**
  - 理由：AIは「確認を行う」のように表現を膨らませがち。
    情報が増えないまま文が長くなり、読む負担が増える。
  - 基準：既存のtextlintルールで冗長な表現を検出する。

- **助詞と接続を重ねない**
  - 理由：AIは同じ助詞や「〜が、〜が、」の接続で節をつなぎがち。
    どの語がどこにかかるかが分かりにくくなる。
  - 基準：1文に同じ助詞が近くで2回以上ある。
    「も」「や」の並列と、自然な文でも重なりやすい「に」「が」は対象外とする。
    接続助詞の「が」が1文に2回以上ある。

- **二重否定を使わない**
  - 理由：AIは断定を避けようとして「〜なくもない」のように否定を重ねがち。
    肯定か否定かを読み手が組み立て直す必要がある。
  - 基準：既存のtextlintルールで二重否定を検出する。

- **読点を打ちすぎない**
  - 理由：読点が多い文は、条件や操作を1文に詰め込んでいることが多い。
  - 基準：1文に読点が4つ以上ある。
    名詞を並べる読点は数えない。

- **参照をたどれるようにする**
  - 理由：AIはファイルや見出しを変更しても、参照元の更新を漏らしがち。
    リンクが切れると、手順を実行するときに必要な情報へたどり着けない。
  - 基準：ローカルのリンク先ファイルとアンカーが存在する。

- **ファイルを長くしすぎない**
  - 理由：決まりが増えるほど、読み落としや決まり同士の食い違いが起きやすい。
    長くなったファイルは、内容を見直すか分割する時期と考える。
  - 基準：文章の行が、SKILL.mdで80行、そのほかのファイルで100行を超える。
    コードブロック・表・HTMLは数えない。

数値は見直す箇所を拾う目安とし、直し方は書き手が判断する。

整形では文の区切りで改行し、表・箇条書き・字下げをそろえる。
文章とコードの内容、Markdownの構造を保つ。

## コマンド

Node.js 22以上を使い、リポジトリのルートで実行する。

```sh
npm --prefix scripts/ai-docs ci --ignore-scripts
npm --prefix scripts/ai-docs run lint -- --all
npm --prefix scripts/ai-docs run links -- --all
npm --prefix scripts/ai-docs run fmt -- --all --check
npm --prefix scripts/ai-docs run fmt -- --all
npm --prefix scripts/ai-docs run lint -- --strict dot_codex/skills/task-dispatch/SKILL.md
npm --prefix scripts/ai-docs run fmt -- dot_codex/skills/task-dispatch/SKILL.md
```
