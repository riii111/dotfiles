# 明日の予定を作る

予定作成の実行で、照合の後に順に行う。
予定で聞いた問いへの返事で再判定するときは、[着手できるか判断する](#着手できるか判断する)を使う。

## 候補を台帳に追加する

`config.yaml`の`sources`のクエリを`gh search issues --sort created --order desc --limit 100`で実行する。
結果に`add`のIssueを加え、`exclude`のIssueを除く。
そのうち台帳にないkeyを`discovered`で追加する。
keyの作成と重複の確認は[itemの規則](item.md#key)に従う。
結果が100件に達したら予定に書く。
読めないitemがある実行では、新しい項目を追加しない。
`sources`にないリポジトリやクエリは調べない。

## 着手できるか判断する

各項目の`attempts`を読んでから、`discovered`・`needs_decision`の項目を判定する。
`needs_decision`は、最後に`needs_decision`へ移した記録より新しい変更がある場合だけ判定し直す。
対象の変更は、Issue本文の編集、IssueまたはPRへの`owner`のコメント、決めたことのメモへの追記、ownerによる仕事の種類の指定とする。
ただし、`kind`が`research`のまま調査を終えて`needs_decision`にした項目は、ownerが仕事の種類を指定したときだけ判定し直す。
終えた調査を、実装へ進むかの答えより前に再開しないため。
判定したら、結果が同じでも`status`を記録する。

次の2点を両方満たせば`ready`、それ以外は`needs_decision`にする。

- Issue本文とそこからリンクされた文書を読めば、ゴールと受け入れ条件が分かる。
- 大きな設計判断に未承認のものが残っていない。

`kind`が`research`の項目は、調べることがIssue本文か決めたことのメモで分かれば`ready`にする。
未承認の大きな設計判断は、調べる対象として扱い、`needs_decision`の理由にしない。

大きな設計判断とは、仕様・公開インターフェース・互換性・担当範囲など、後から変えるコストが大きい判断を指す。
承認として扱うのは、`owner`が書いたIssue本文・コメント・リンク先の文書と、決めたことのメモにある決定だけとする。
その他の未決事項は、workerが暫定で決めて完了報告に書き、朝の報告で確かめるため、ここでは問わない。

大きな設計判断で`needs_decision`にした項目は、`question`に人に聞く問いを1つ、選択肢と推奨を付けて自分の言葉で書く。
答えが来て判定し直すまで、毎回の予定で聞き続ける。

## 明日の予定を作成する

明日始める項目と聞く問いを選び、[予定の書き方](digest.md#明日の予定)で`runs/<日付>-plan.md`に書く。
新規起動の項目ごとに`attempts`へ`planned`を追記する。
前回までの`planned`のうち使われていないものには、先に`plan_cancelled`（note：再計画）を追記する。

優先順は、GitHub Projectの優先度・期限とIssueの依存関係（blocked by）に従う。
AIはビジネス上の優先順位を決めない。
順位が付かない項目どうしは、Issueの作成日が新しい順にする。
新規起動は、最初に選んだ項目と親Issue・リンク先・ラベルが同じ項目を先に載せ、1回の予定で案件や方針が散らばらないようにする。
関連する項目が枠に足りなければ、残りは作成日の新しい順で埋める。

既存workerへの続行は[続行の送信](continue.md)に従って早朝の実行で扱い、候補表には新規起動だけを載せる。
続行にはOKも`planned`の記録も不要。

新規起動は`ready`の項目から選ぶ。
先に、項目ごとに[PRの積み方](../../task-session-launch/references/stacking.md)の基準で積み方を決める。
積むときは積み先のPRを選び、`planned`のnoteに`積み先=<PR番号>`を足す。
同じ予定で、複数の項目が同じPRを積み先にしないようにする。
そのうえで、[起動の確認](launch.md#起動の確認)を通ったものを載せる。
積み方は[予定の書き方](digest.md#明日の予定)で予定に書き、OKと一緒に承認を受ける。
依存が未完了の項目は、積み先にできるPRがなければ載せず、`next_action`に依存先を書く。

新規起動は[新規起動する件数](launch.md#新規起動する件数)の枠まで載せる。
予定を書いたら、[スレッドを記録](schedule.md#スレッドの扱い)し、[Scheduled Taskを削除](schedule.md#scheduled-taskの扱い)する。
[スレッドでのやりとり](digest.md#スレッドでのやりとり)に従って予定とOKの返し方を返し、ユーザーの返事を待つ。
