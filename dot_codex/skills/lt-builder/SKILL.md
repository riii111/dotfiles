# LT Builder

LTは急に振られたり、しばらく間が空いたりするので、作り方を忘れやすい。
このスキルは、作り方の手順と、各段階で確認することを固定する。

## 進め方の原則

**一度に全部作らない。**
フェーズごとに成果物を出し、区切りで止まる。
題材の理解が浅いままスライドまで進むと、手戻りが大きくなるからだ。

- 次のフェーズへは、ユーザーの明示的な合図で進む。
  修正指示は、同じフェーズ内での反復として扱う。
- ユーザーが到達点を指定したときは、そこまで続けて進めてよい。
  例：「カンペまで作って」
- フェーズは一方通行ではない。
  練習とカンペは往復してよい。
  前提の誤りが分かれば前のフェーズに戻る。
- 区切りや判断が必要なときだけ、現在地と次の選択肢を一行で示す。
- 途中から始めた場合は、該当するフェーズから始める。
  前の成果物の不足は、困るときだけ確認する。

自分の判断で進めてよいのは、フェーズ内の自己レビューと修正の反復だけ。
ユーザーが他のAIのレビュー結果を貼ったら、同意する点と同意しない点を理由つきで分けて返す。

次のことは、ユーザーの確認を取る。

- 到達点の指定がない場合のフェーズの移動
- 別のAIによる独立レビューの利用。
  ツールやモデル、費用はユーザーが決める
- Slackなどへの送信と、資料の公開。
  下書きまでは作ってよい
- 保存先の変更、Git管理への追加、チーム向けドキュメント化

## フェーズ一覧

| Phase | やること                   | 成果物                             | 区切りの目安                             |
| ----- | -------------------------- | ---------------------------------- | ---------------------------------------- |
| 0     | 枠の確認                   | 一行の発表ブリーフ                 | 時間・聞き手・型・保存先が決まった       |
| 1     | 事実の収集                 | コンテキストメモ                   | 時系列と判断の経緯が追える               |
| 2     | 方針メモと外部視点レビュー | レビュー結果、更新したメモ         | 主張が3つ以内に絞れ、山場の説明が通る    |
| 3     | スライド化                 | スライド原稿                       | 伏線が回収され、メッセージが固有になった |
| 4     | 洗練                       | 削った原稿                         | 見積もり時間が枠に収まる                 |
| 5     | 転記と練習                 | 発表ツール上の資料                 | 通し練習の実測が枠に収まる               |
| 6     | カンペ                     | 時間の目安、短縮ポイント、想定質問 | ユーザーが使える状態と判断               |
| 7     | 事後対応                   | 返信の下書き、事例の追加           | 下書きをユーザーに渡した                 |

Phase 4から7の詳細は [後半フェーズ](references/later-phases.md) にある。

## Phase 0：枠の確認

最初に、まとめて一度だけ聞く。
3問までにして、分かっていることは聞かない。

- 時間と質疑の有無、発表日と練習できる時間
- 聞き手の前提知識と英語話者の有無。
  英語話者がいれば、日英併記にするかと、発表ツールでできる表現を確認する
- 題材のネタ元と、資料の保存先・公開範囲

聞いた内容から、[発表の型と聞き手の幅](references/talk-types.md) を決め、ユーザーに一言で確認する。
型によって、集める材料、レビューの観点、構成の骨組み、想定質問が変わる。

## Phase 1：事実の収集

[事実の収集](references/context-collection.md) と、型ごとの材料を読んで進める。
どの型でも、最後に発表者へのインタビューで動機や迷いを補う。

成果物は [コンテキストメモ](references/templates.md#コンテキストメモ)。
記録で確認できる事実、発表者の認識と振り返り、AIの提案や解釈を混ぜない。
混ぜると、後知恵の美化や、記録にない合意を事実として話す事故が起きる。

## Phase 2：方針メモと外部視点レビュー

[Phase 2の4観点](references/review-lenses.md#phase-2の4観点) で読む。

**読み手の役割を明示する。**
「題材を知らない聞き手として読む」と宣言してから読む。
内部の人には当たり前の用語や経緯を、遠慮なく「分からない」と言うための宣言だ。

- 4観点の3つめは方針転換型のもの。
  他の型では、発表の型に合わせて差し替える
- 疑問は最大5件に絞る。
  多いとユーザーが答えきれず、反復が止まる
- 課題や論点は、この段階では削らない。
  出し切ってから分類し、削るのはPhase 4で行う
- 更新版には、良くなった点を短く述べてから、残る弱点を優先度順に出す

## Phase 3：スライド化

**情報量を三層に分ける。**
コンテキストメモにはすべてを、スライドには聞き手が目で追う最小限を置く。
残りは口頭補足とカンペに回す。
スライドを短くするときは、正確さを保ったまま詳細を下の層へ移す。

構成は型ごとの骨組みから始め、同じ型の [事例](references/examples.md) があれば効いた工夫を確認する。
冒頭で結論か一番の見どころを出し、発表枠と前提知識に応じて題材を短く説明する。
学びは一つのパンチラインに絞り、「以前の案を捨てた物語」を無理に作らない。

図は、**意思決定の構造が見える粒度**にする。
比較する図同士は、同じ形式・同じ登場人物で揃える。

レビューは [Phase 3の観点](references/review-lenses.md#phase-3の観点) で行う。

## 振る舞いの注意

- **明確に不採用とされた提案は、新しい根拠がない限り繰り返さない。**
  返事がないまま2回伝えたものは、必要ならカンペの想定質問に回す。
- **意図的に外したものは、理由を受け入れる。**
  提案するなら、文字や枚数を増やさない代替だけにする。
  外した内容と理由はコンテキストメモに記録する。
- **ユーザーが手で編集した後は、必ず読み直す。**
  修正は指定された箇所だけにする。
- **推測と事実を分ける。**
  読めなかった資料は読めなかったと言い、推測で補わない。
- **一般論で評価しない。**
  評価には、その発表の具体的な箇所を根拠として添える。
- **過去の自分の指摘が間違っていたら、先に訂正する。**
