# 発表の型と聞き手による調整

Phase 0で型と聞き手の幅を決め、以降のフェーズで下の表に従って観点を差し替える。
型は混ざってよい。
主になる型を一つ決め、従になる型の観点を必要な分だけ足す。

迷ったら、ユーザーに「この発表で聞き手に一番持ち帰ってほしいのは、判断・やり方・技術・作ったもの、のどれか」と聞く。

## 型の一覧

| 型           | 典型的な題材                                            | 山場                                       | 実例 |
| ------------ | ------------------------------------------------------- | ------------------------------------------ | ---- |
| 方針転換型   | 設計を選び直した、移行した、やめた                      | 前提の何が変わり、判断が変わったか         | あり |
| 手法型       | 要件を設計に落とすやり方、ADRの書き方、レビューの進め方 | 手法を当てたら何が見えたか                 | —    |
| 技術紹介型   | 言語・ツール・技術の紹介や布教                          | 見え方が変わる視点（例：制約が武器になる） | —    |
| 作ってみた型 | 趣味の開発、新技術の試用                                | 一番詰まったところと、その解き方           | —    |

実例の詳細は [過去の発表事例](examples.md) にある。
実例のない型は、下の骨組みと「型ごとの工夫」から始める。

## フェーズごとの調整

### Phase 1：材料と裏取り

| 型           | 主な材料                                                  | 裏取りで気をつけること                                       |
| ------------ | --------------------------------------------------------- | ------------------------------------------------------------ |
| 方針転換型   | Slack、PR、ADR、議事録                                    | 時系列。当時の認識と今の振り返りを分ける                     |
| 手法型       | Epic・要件、ADR、図（モデル・状態遷移）、レビューでの議論 | 手法の定義は一次出典（提唱者の文章、公式の用語集）で確認する |
| 技術紹介型   | 公式ドキュメント、採用事例、調査結果、自分のコード例      | 数値・順位・事例は出典と時点を確認する。古くなりやすい       |
| 作ってみた型 | コミット履歴、デモ、計測結果、失敗した実験                | 記録にない動機や迷いをインタビューで補う                     |

### Phase 2：4観点のうち「後知恵」の差し替え

「後知恵で当初の判断を不当に悪く見せていないか」は方針転換型の観点。
他の型では、同じ位置に次の観点を置く。

| 型           | 差し替える観点                                                                                                                |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 手法型       | **一般化しすぎていないか。** この案件で効いた理由と、どこでも効く部分を分けているか。手法の定義の説明が長くなりすぎていないか |
| 技術紹介型   | **持ち上げすぎていないか。** 向かない場面、難しいところ、主観であることを示しているか                                         |
| 作ってみた型 | **自分の頭の中だけにある前提が抜けていないか**                                                                                |

### Phase 3：構成の骨組み

どの型も、冒頭で結論（または一番の見どころ）を出し、発表枠と聞き手の前提知識に応じて題材を短く説明してから入る。
学びは一つのパンチラインに絞る。

- **方針転換型**：当時の判断と理由 → 進めて分かったこと → 判断が変わった山場 → 学び
- **手法型**：題材の特徴 → なぜこの手法が要ったか（何が決まっていなかったか） → 手法をどう当てたか（判断基準つき） → 当てて見えたこと・決められたこと → 改善余地 → 学び
- **技術紹介型**：最小限のコード例で雰囲気をつかむ → 難しいところ（正直に） → 見え方が変わる視点 → 向く場面・向かない場面 → 事例 → 学び
- **作ってみた型**：作ったもの・デモ → 一番詰まったところと解き方 → 計測結果や失敗した実験 → 学び

### 型ごとの工夫

骨組みを肉付けするときの改善候補。
事例に載せなかった過去の発表から得たもので、手本の資料はない。
どれも一度の経験に基づくので、題材に合うかを確かめてから使う。

- 根拠：手法型は社内LT1件（Epicの分析からADRとドメインモデルへ落とした発表）。
  技術紹介型は他部署を含む合同LT1件（プログラミング言語の紹介）
- 適用条件：同じ型で、聞き手が近い場合

**手法型**

- 手法を使う判断基準を、聞き手が持ち帰れる形で示す。
  例：ADRに書く候補は「解釈が分かれそう」「巻き戻しコストが高そう」「複数のタスクの前提になりそう」「数ヶ月後に説明がしんどそう」
- 手法で扱う範囲と扱わない範囲を明示する（例：ADRには実装手順ではなく「意味」を書く）
- 手法を当てた結果が、別の設計にどう効いたかを具体的につなげる。
  例：状態遷移図で「状態として持つもの」と「理由として残すもの」を分けたら、テーブル設計が決まった
- 入力や場面ごとの判断結果を列挙すると、手法の効果が見える
- 手法の定義は一次出典で短く済ませる。
  定義の説明を長くしない
- 改善余地を自分で挙げる

**技術紹介型**

- 難しいところを先に正直に出してから、見え方が変わる視点を出す。
  布教一辺倒にしない
- 主観であることを最初に断り、向かない場面も示す
- コード例は短くし、各行の意味を添える
- 採用事例は「どこで、なぜ局所的に使われているか」の形で示す。
  数値は発表時点で出典を確認する
- 中心の主張を冒頭で予告しておくと、難しいところのパートが伏線として効く

### Phase 6：想定質問の型の重み

| 型           | 特に用意する質問                                                           |
| ------------ | -------------------------------------------------------------------------- |
| 方針転換型   | 代案、目的は達成できたか、もっと早く気づけなかったか                       |
| 手法型       | 毎回やるとコストが重くないか、どの規模から効くか、チームでどう定着させるか |
| 技術紹介型   | うちのプロダクトで使うべきか、学習コスト、採用時のリスク                   |
| 作ってみた型 | なぜその技術か、実運用に耐えるか                                           |

## 聞き手の幅

| 聞き手                 | 調整                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 同じチーム・プロダクト | 内部用語は最低限の説明でよい。経緯の細部に価値がある                                                             |
| 開発組織全体           | 題材の説明に時間を確保する（15分枠なら1分程度）。内部用語・略語は定義するか言い換える                            |
| 他部署を含む合同       | 自己紹介を入れる。コードは最小限で、読まなくても話が分かるようにする。社外秘・顧客情報が含まれていないか確認する |
| 英語話者を含む         | 日英表記をPhase 0で決める。[日英表記の指示](templates.md#日英表記の指示) を使う                                  |
