# 事実の収集

## 共通の原則

- **事実・振り返り・AIの提案を分ける。**
  コンテキストメモの節を分けるか、各記述に出典を付ける
- **リンクには確認状況を付ける。**
  「本文を確認済み」「スレッドのみ確認」「未確認」など。
  後で読み返したとき、どこまで信じてよいかが分かる
- **固定版のリンクを残す。**
  PRやドキュメントは、コミットハッシュつきのURLにしておくと内容が変わらない
- **記録に残っていないことは、発表者に確認する事項として書き出す。**
  推測で埋めない。
  例：会議での具体的な発言、正式な決定日
- **時系列を作る。**
  「いつ、何が分かり、何を判断したか」が並ぶと、山場の説明が通りやすくなる
- **記録を集めた後に、発表者へインタビューする。**
  本業でも、当時の認識や迷いは記録に残っていないことが多い。
  質問は [インタビューの質問](#インタビューの質問) を使う

## 本業の案件の場合

集める材料：

- Slackの議論（判断の経緯、懸念が出た時期）
- GitHubのIssue・PR・ADR（決定事項、不採用案と理由、レビューでの指摘）
- 議事録・設計ドキュメント
- 関連する兄弟プロダクトの事例（似た課題をどう解いたか）

注意：

- 社内限定資料は、読むAIや聞き手のアクセス権で取得できない場合がある。
  メモにその旨を書いておく
- 議論の途中で列挙された案を、採用された案と混同しない
- 中止や方針転換の「単一の原因」を断定しない。
  記録から言えるのは、判断の材料が積み上がった経緯まで

## 趣味の開発の場合

議論の記録がない代わりに、次を材料にする。

- コミット履歴（何をいつ変えたか、大きな書き直しの時期）
- Issue、README、TODOメモ
- 自分のメモ、作業ログ、SNSへの投稿

- デモ、試作品、捨てたブランチ
- 失敗した実験と、その計測結果
- ベンチマークやプロファイルなどの計測結果

趣味の開発では、他人との合意がない分、**自分の頭の中だけにある前提**が説明から抜けやすい。
Phase 2のレビューでは「後知恵」の観点に加えて、この観点でも読む。

## インタビューの質問

本業・趣味共通。
記録で分かることは聞かない。

- 何がきっかけで作り始めたか。
  最初に解きたかった問題は何か
- 最初に選んだ技術・構成と、その理由。
  他に候補はあったか
- 一番時間がかかった、または詰まったところはどこか
- 途中で作り直した・方針を変えたところはあるか。
  何がきっかけか
- 今振り返って、最初からこうすればよかったと思うこと。
  ただし当時それを選べなかった理由も
