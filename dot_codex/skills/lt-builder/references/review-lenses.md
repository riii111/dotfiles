## Phase 2の4観点

題材を知らない聞き手として、方針メモを読む。

### 1. 持ち帰れるノウハウ

聞き手が自分の仕事に転用できるものを挙げる。
題材固有の事情を外しても成り立つかで判断する。
強い順に並べ、主軸から外れるもの（実装の小技など）は「主軸とは別」と明記する。

### 2. 理解できない箇所（最大5件）

- 題材の前提（何の機能か、誰が嬉しいか、関係者は誰か）
- 内部用語・略語
- 構成や経緯の中で、図がないと追えないもの
- **判断の理由が書かれていない箇所**。
  特に、以前見送った案を採用し直すなど、判断が変わる箇所

### 3. 後知恵で当初の判断を不当に悪く見せている箇所

方針転換型の観点。
他の型では [発表の型](talk-types.md#phase-24観点のうち後知恵の差し替え) の観点に差し替える。

- 比較表で新旧を並べたとき、旧案が当然の誤りに見えないか。
  当時の前提を同じ表に入れる
- 「進めて分かった負担」が「最初から分かったのでは」に見えないか。
  想定していたが量が想定を超えたのか、想定していなかったのかを分ける
- 「当初から別案もあると感じていた」は、自己正当化や後付けに聞こえる。
  言うなら、当時それを退けた理由とセットにする
- 本来の目的以外の動機（経験を積みたかった等）は、後から「やりたかったから」に見えやすい
- 逆に、**当初の判断で今も正しいもの**が埋もれていないか探す。
  それを示すと発表全体の信頼が上がる

### 4. 削るべき論点

- 主軸と別の実装詳細
- 採用されなかった案の列挙
- 技術比較の一般論（深入りすると時間が足りなくなる）
- 「伝えたいこと」が4つ以上あるなら、3つに絞る案を出す
- 結論に入るまでの時間が長すぎないか（冒頭で結論を出す構成を提案）

## 山場の確認（判断が変わる発表の場合）

方針転換型では、判断を変えた瞬間が発表の山場になる。
次の問いに答えられるかを確認する。

- **前提の何が変わったのか。**
  懸念が消えたのか、比較相手が変わったのか。
  例：「まだ見ぬ案A」との比較が、「実体化した案Aの負担」との比較に変わった
- **一つの前提が複数の判断を支えていなかったか。**
  その前提を外したとき、以前見送った複数の案がまとめて選べるようになることがある。
  これは発表で一番持ち帰られやすい学びになりやすい
- **新しい案で何が解消し、何が移り、何が残ったか。**
  新案を万能に描かない

## Phase 3の観点

- **伏線の回収。**
  課題を積み上げたなら、最終案でそれぞれがどうなったかが分かるか。
  スライドを増やせない場合は、課題を根本原因の形にまとめ、最終案をその裏返しとして示す
- **選んだ基準が見えるか。**
  「一番シンプル」「許容できる負荷」だけでは定性的すぎる。
  前半で挙げた根本原因を、そのまま比較軸として回収できないか
- **メッセージが固有か。**
  どの発表でも言える一般論になっていないか。
  この経験からしか出てこない言葉に置き換えられないか
- **引用や法則の使い方。**
  有名な法則を出すなら、結論とつながるか確かめる。
  例：コンウェイの法則なら「写す単位を間違えていた」のように接続する
- **終盤の文字量。**
  聞き手は終盤ほど疲れている。
  正確さを保ったまま短くし、詳細は口頭補足やカンペへ移す
- **技術的に突っ込まれる言葉。**
  用語の誤用、不正確な注記がないか。
  特に、分野の専門用語を別の意味で使っていないか。
  例：SREの「症状ベースのアラート」と、一次対応の担当分担を混同する。
  誤りや誤解を招く表現は本文を直す。
  正確だが説明を省いた詳細は、カンペの想定質問に回す

## スライド文体

- 語尾の「〜した」「〜と感じた」「〜必要がある」は、体言止めか「〜へ」「〜は未整理」で切る
- 一文に二つのことが入っていたら、改行か箇条書きに分ける
- タイトルと同じことを本文の1行目で繰り返さない
- 図を見れば分かる前置きは1行にする
- 口語（「さすがに大変」など）は、LTの温度感として残してよい
- 表のセルは短く。
  行は2〜3行あれば趣旨は伝わる

## 既定の好み

ユーザーの過去の指示から得た既定値。
ユーザーが別の指示をしたらそちらに従う。

- スライドの文末に句点を付けない
- 同じ説明を複数のスライドで繰り返さない
- AI的な抽象語（「〜を実現」「価値を最大化」など）を避け、具体的な言葉にする
- リンクは、各スライドの末尾に並べず、主要な箇所の既存の文言に埋め込む。
  参考資料は最後の1枚にまとめる
- 構成を比較する図はシーケンス図で揃え、所有や配置（どのチーム・どの基盤か）はboxで示す

## 想定質問の型

次の型で洗い出し、一次回答を短く用意する。

| 型                     | 例                                                                 |
| ---------------------- | ------------------------------------------------------------------ |
| 代案                   | 「〇〇アーキテクチャじゃダメだったの？」「〇〇を使えば？」         |
| 目的の達成             | 「結局、当初の目的（独立してリリースしたい等）は達成できたの？」   |
| 残った課題の扱い       | 「残ると言っていた〇〇はどう解決するの？」                         |
| データ・セキュリティ   | 「データを外部に渡して大丈夫？」「保持しないことをどう担保する？」 |
| 後知恵                 | 「もっと早く気づけなかったの？」                                   |
| 用語・注記への突っ込み | スライド中の不正確な言い回し                                       |
| 前提知識               | 「そもそも〇〇はなぜアンチパターンなの？」                         |

回答は「確認済みの方針」と「未決事項」に分ける。
未決事項について、AIが答え方の候補を出すのはよい。
例：「頻度が分からないので、まず検知して計測してから範囲を決める」
候補であることを明記し、採用はユーザーが決める。
