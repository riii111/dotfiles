# ADR Review

## 調査の分担

ADRと、関連するEpic・要件・業務規則・過去の決定を読む。
不足する文脈は未確認として扱う。
[調査の分担](../ai-code-review/references/review-delegation.md)に従い、独立して検証できる主張や調査先ごとに分担する。

## 主張と証拠

ADRを意思決定に関係する主張へ分解する。
一文に複数の主張があれば分け、同じ主張を支える複数の文はまとめる。
主張ごとにID・内容・意思決定に重要な理由を記録し、次の情報源から証拠を集める。

- `repo`: 原則として必須
- `infra`: 運用・監視・権限・展開・外部連携・環境構成に触れる場合
- `docs`: ベンダーの挙動・製品上限・外部契約に依存する場合
- `live`: 「頻繁に」「高負荷」「高コスト」「劣化」など、現在の実態を主張する場合

情報源が不明ならユーザーに確認する。
存在するだけの情報源には広げず、主張の検証に必要な範囲を調べる。

次の場合は重いレビューとし、主張ごとに情報源・裏付けの強さ・証拠メモを内部で整理する。
それ以外では、主張が曖昧か影響が大きい場合を除き、詳細な証拠マトリクスは省略する。

- 性能・費用・移行・監視・ロールバック・可用性に関する主張
- 現在の問題の頻度・規模・費用・劣化に関する主張
- 複数リポジトリの依存関係、または信頼境界の変更

裏付けは `supported`（支持する証拠がある）・`contradicted`（証拠と食い違う）・`unverified`（証拠不足）で区別する。

## レビュー観点

- 設計: 責務とロジックの配置、抽象化、代替案、既存設計との一貫性、問題を解決するか
- 要件を扱う場合: 要件・受け入れ条件との整合、不足や範囲のずれ、過剰な対応
- 実現性: 実装・移行の現実性、運用負荷、必要性、より小さく価値を得る方法
- 安全性に触れる場合: 認証・認可、データ公開・テナント分離、秘密情報・設定、信頼境界の前提

## コメントの絞り込み

各懸念は次の順で判断する。

1. 対象の主張と根拠を特定する。
2. 証拠が裏付ける最小の命題へ絞る。
3. 残す・弱める・取り下げるを決める。
4. 重要度を付け、コメントを書く。

具体的な失敗条件のない抽象的な懸念は、分解するか取り下げる。
影響が大きくても証拠が弱い懸念は、重要度を上げず未確認の前提として扱う。

| 影響 × 証拠               | 重要度        |
| ------------------------- | ------------- |
| 大きな影響 + 強い証拠     | MUST          |
| 中程度の影響 + 強い証拠   | SHOULD        |
| 大きな影響 + 中程度の証拠 | SHOULD        |
| 小さな影響 + 強い証拠     | NITS          |
| 中程度の影響 + 弱い証拠   | NITS または Q |
| 大きな影響 + 弱い証拠     | 未確認の前提  |

現在のリポジトリの文脈に結び付け、今の不正確さ・危険と将来の改善を区別する。
完全な設計を求めず、可能なら実行可能な最小の修正をコメントに含める。
設計全体に関わる話はレビューの結論で説明する。

## 出力

[review-report.md](templates/review-report.md)でMarkdownレポートを作成し、「このADRは何を決めるのか」は[explain-change](../explain-change/SKILL.md)に従って説明する。
コード・ADR自体は変更せず、チャットには短い結論とレポートへのリンクを返す。

- テンプレートの3セクションと候補ごとの項目を使い、空欄・プレースホルダー・不要な注記は残さない。
- 投稿候補の行リンクは検証済みコミットの変更側に実在するものを使う。
  全体コメントに架空の行リンクを付けず、既存スレッドと重複する指摘は出さない。
- 直接URLは確認済みの実装・仕様・Issue・公式資料に限る。
- 主張整理・証拠マトリクス・取り下げた候補・取捨選択の経緯は内部に留める。
  補足は判断を左右する未確認事項がある場合だけ加える。
- PRへの投稿・返信・レビュー送信は行わず、コメントは下書きにする。
  resolveの許可は推測しない。
