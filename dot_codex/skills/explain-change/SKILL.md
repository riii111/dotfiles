# explain-change

説明は読み取り専用とし、単独の解説依頼ではレビュー判定を行わない。

## 対象と根拠

- 指定されたPR・差分範囲・ADRと適用されるリポジトリ規約を読む。
- 差分の前後、必要な呼び出し元・型・テスト・関連ADRをたどる。説明に必要な根拠がそろったら調査を止める。
- コードで確認できる挙動、資料に記された設計理由、自分の推測を区別する。ADRの提案を実装済みの挙動として扱わない。

## 説明

開発者としての知識を前提に、対象とユーザーの理解に合わせて短く説明する。Markdownを基本とし、HTML/CSS/JS生成や外部公開を既定にしない。

### 全体像をつかむ

- 具体的な利用場面や入力から、変更前後の違いと設計判断をつなぐ。内部整理なら、挙動が変わらないことと責務の変化を示す。
- 処理の流れ・責務の関係・状態遷移は図を入口にする。Mermaidなどアプリで読める図を使い、単純な変更で理解を助けない場合は省略する。
- 図は役割が伝わるラベルに必要な関数・オブジェクト名を添え、呼び出し・結果返却・状態更新の関係を示す。データ型自体を動作の主体として描かない。
- 文章は図の流れを繰り返さず、設計理由と例外を補う。理解を左右する制約・未確認事項は省略しない。

### 実コードでつなぐ

実装コードがある場合は、代表的な経路を短い抜粋で示す。

- 具体的な入力から、誰が値を更新・返却し、誰がそれを読んで分岐や次の動作を決めるかをつなぐ。
- 図もある場合は、抜粋がどの段階に対応するかを明確にする。
- 説明は抜粋で確認できる挙動に対応させる。抜粋外の重要な条件は決定箇所へ根拠をつなぐか、抜粋を選び直す。
- 設計上の利点は変更前後の具体的な構造に結び付ける。

### 根拠をたどり、必要な箇所を深める

要点の近くにコード・テストのファイルと行、ADRの節へのリンクを添える。続く質問では必要な箇所だけ掘り下げる。
