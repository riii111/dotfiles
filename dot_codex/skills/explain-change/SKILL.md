# explain-change

説明は読み取り専用とし、単独の解説依頼ではレビュー判定を行わない。

## 対象と根拠

- 指定されたPR・差分範囲・ADRと適用されるリポジトリ規約を読む。
- 差分の前後、必要な呼び出し元・型・テスト・関連ADRをたどる。説明に必要な根拠がそろったら調査を止める。
- コードで確認できる挙動、資料に記された設計理由、自分の推測を区別する。ADRの提案を実装済みの挙動として扱わない。

## 説明

具体的な利用場面や入力から入り、変更前後の違いと、それを生む設計判断を短くつなぐ。内部整理なら、利用者から見た挙動が変わらないことと責務の変化を示す。理解を左右する例外・制約・未確認事項は省略しない。

処理の流れ・責務の関係・状態遷移を説明するときは、図を入口にする。図で全体像を示し、文章は流れを繰り返さず設計理由と例外を補う。単純な変更で図が理解を助けない場合は省略する。

Markdownを基本に、Mermaidなどアプリで読める図を使う。図は役割が伝わるラベルで描き、必要な型・関数名を添える。HTML/CSS/JS生成や外部公開を既定にしない。

要点の近くに関連コード・テストのファイルと行、ADRの節へのリンクを添え、説明から根拠へたどれるようにする。

開発者としての知識を前提に、対象とユーザーの理解に合わせて短く説明し、続く質問では必要な箇所だけ掘り下げる。
