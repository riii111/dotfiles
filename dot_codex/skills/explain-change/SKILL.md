# explain-change

変更を初めて読む開発者が、何が変わり、なぜその設計で、どこを読めば確かめられるかを理解できる説明にする。

## 対象と根拠

- 指定されたPR・差分範囲・ADRと適用されるリポジトリ規約を読む。対象が特定できない場合だけ確認する。
- 差分の前後、必要な呼び出し元・型・テスト・関連ADRをたどる。説明に必要な根拠がそろったら調査を止め、網羅的なレビューへ広げない。
- コードで確認できる挙動、資料に記された設計理由、自分の推測を区別する。理由の記載がなければ推測と明示し、ADRの提案を実装済みの挙動として扱わない。

## 説明

具体的な利用場面や入力から入り、変更前後の違いと、それを生む設計判断を短くつなぐ。内部整理なら、利用者から見た挙動が変わらないことと責務の変化を示す。理解を左右する例外・制約・未確認事項は省略しない。

処理の流れ・責務の関係・状態遷移を説明するときは、図を入口にする。図で全体像を示し、文章は流れを繰り返さず設計理由と例外を補う。単純な変更で図が理解を助けない場合は省略する。

Markdownを基本に、Mermaidなどアプリで読める図を使う。実在の型・関数・処理名を図に活かす。HTML/CSS/JS生成や外部公開を既定にしない。

要点の近くに関連コード・テストのファイルと行、ADRの節へのリンクを添え、説明から根拠へたどれるようにする。テストを読んだだけなら、実行で確認したとは書かない。

変更ファイルの列挙や固定テンプレートの穴埋めにしない。全項目や図の数を強制せず、対象とユーザーの知識に合わせて短い入口を作り、続く質問では必要な箇所だけ掘り下げる。技術常識の過剰な解説、子供向けの比喩や文体を避ける。理解確認クイズや追加承認を強制しない。

## 権限と役割

理解支援は読み取り専用。コード修正、commit、レビューコメント投稿、approve、resolve、PRのReady化などの状態変更は含めない。単独の解説依頼をコードレビューへ広げず、LGTMなどのレビュー判定を付けない。ユーザーがcode-reviewやadr-reviewとの併用を指定した場合は、その依頼の範囲を保つ。

既存レビューSKILLやtask-*の自動完了報告から起動する用途には使わない。
