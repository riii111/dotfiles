# AI Code Review

実装・PR操作は行わない。
指摘をGitHubのPendingレビューへ保存するのは、ユーザーが `review-draft` を呼んだときだけとし、このSKILLでは保存しない。
結果の送信はユーザーが承認した宛先・手順に従い、この SKILL の選択だけで送信権限があるとは扱わない。

## フェーズ一覧

1. [調査と判定](#1-調査と判定)
2. [返す内容](#2-返す内容)

## 1. 調査と判定

[共通レビュー基準](references/review-core.md) を全文読み、調査・分担・採否・検証に従う。
リポジトリ固有の技術・業務規約を根拠に使い、別のレビュー SKILL の回答形式で置き換えない。

依頼された base・head・checkout を確認する。
SHAが一致しない場合や、判定を左右する根拠が取得できない場合は「判定保留」とし、具体的な不足を返す。
未実施の網羅的テストがあることだけでは保留にしない。

## 2. 返す内容

判定と指摘は、本体が直接、次の形式で返す。
指摘を理解・修正するための前提と因果関係は残す。

```markdown
判定: LGTM / 修正必要 / 判定保留
対象: <base SHA>...<head SHA>（<checkout、PRがあればURL>）

## Blocking

- <ID> <問題の要点> — <確認版のファイル・行>
  - 条件と影響: <具体的な入力・操作・状態で何が問題になるか>
  - 根拠: <コード・仕様・再現結果。確認と推測を区別>
  - 必要な修正: <満たすべき挙動。方法が一意でなければ実装を指定しない>
  - 検証: <修正確認に必要なケースがあれば記載>

## Non-blocking（任意）

- <ID> <改善案> — <場所、現在の負担や重複、改善の価値>

## 確認範囲・未確認事項

<実施した検証の結果と、判断に影響する未確認事項だけ>
```

空の指摘欄は省く。
Blocking があれば「修正必要」、判定に必要な確認が不足していれば「判定保留」、それ以外は Non-blocking が残っていても「LGTM」とする。

再レビューは指定差分全体を確認し、前回の解決済み指摘を新たな根拠なく再要求しない。
前回の指摘が参照できる場合は、その対応状況（解消・未解消・合意した後続対応）を短く示し、新規指摘と区別する。
既存コメントへの追加確認は対象スレッドへ紐付ける。
呼び出し元に返却形式や宛先の指定がある場合は、この結果をその形式に入れる。
