# review-draft

会話で調整した指摘を、本人のPendingレビューへ保存する。
Pendingは本人だけが見られ、Submit reviewはユーザーがGitHub上で行う。
pr-review・ai-code-review・adr-reviewを実施しただけでは保存しない。

## 保存の道具

`pending-review` だけを使う。
`gh api`、`gh pr review`、GitHubコネクタ、MCPでの直接保存や送信はしない。

- `pending-review` は、認証本人のPendingレビューへの行コメントと既存スレッドへの返信の追加、およびそのPendingレビューにあるコメントの文面の更新だけを行う。
  レビューの送信、resolve、削除、任意のAPI呼び出しは実行できない。
- 引数は取らず、標準入力のJSONだけを読む。
- 保存する前に、認証本人、PRがOPENか、PRのheadが確認版のSHAと同じか、行がPR差分に含まれるか、返信先が対象PRのスレッドかを確認する。
- 保存したコメントの末尾には、見えないマーカー `<!-- pending-review owner=... side=... -->` が付く。
  更新しても元のマーカーは残る。
- 他のチャットが保存したコメントも更新できる。
  サイドチャットで整えた文面を、元のチャットが保存した下書きへ反映する用途がある。
- 本人の手書きコメント（出力で `handwritten`）は、ユーザーが編集を依頼したときだけ更新する。
  手書きコメントにはマーカーも指摘レベルも付け足さない。

## 手順

1. 対象を決める。
   PRのリポジトリ（`OWNER/REPO`）と番号、レビューで確認した版の完全なコミットSHA（40桁、小文字）を会話から読む。
   読めないときだけ聞く。
2. 状態を確認する。
   `add`、`reply`、`update` を空にした入力を送ると、読み取りだけを行う。
   出力の `viewer` が本人のアカウントか、`head` が確認版か、Pendingレビューのコメントを見る。
   コメントごとに、ID、位置、保存元（`owner=...` か `handwritten`）、現在の文面が出る。
   別のチャットで確認版のSHAが会話にないときは、`gh pr view <番号> -R OWNER/REPO --json headRefOid` で読み、ユーザーが示した版と同じか確かめる。
   `viewer` が本人でないとき、`head` が確認版と異なるときは、保存せず状況を伝える。
3. コメントを整える。
   採用済みの指摘を、読み手に伝わる自然な文章にする。
   ユーザーが直した文面と口調を優先し、AIの作業メモや内部の物理名を入れない。
   行コメントの冒頭に[指摘レベル](#指摘レベル)を付ける。
   行番号は確認版のファイルを読んで自分で決め、ユーザーに聞かない。
   返信は `gh-loupe pr review-threads <PRのURL>` で対象のレビューコメントを含むスレッドの GraphQL ID を確認し、指摘レベルを付けずに文面を整える。
   解決済みスレッドには `--include-resolved` を付ける。
4. 保存する。
5. 返答する。

## 指摘レベル

1行目には指摘レベルだけを書き、2行目から本文を書く。
レベルは指摘の重さで選ぶ。

| レベル      | 使う場面                             |
| ----------- | ------------------------------------ |
| `[must]`    | 直さないと不具合や事故になる         |
| `[should]`  | 直したほうがよいが、マージは止めない |
| `[imo]`     | 個人の好みや意見                     |
| `[nits]`    | 表記や体裁などの細かい点             |
| `[suggest]` | 別の書き方の提案                     |
| `[Q]`       | 意図や前提の確認                     |

本文は、ユーザーの傾向に合わせて質問の形を基本にする（「〜の場合に〜になりませんか？」「〜でもよさそうですが、どうでしょう？」）。
`[must]` でも、根拠を添えたうえで言い切りすぎない。

## 入力

`owner` は `add` と `reply` のときだけ必要で、更新と読み取りでは省略できる。
Codexでは環境変数 `CODEX_THREAD_ID` が既定になる。
未設定なら、最初の保存で短い英数字を作り、このチャットの間は同じ値を `owner` に渡す。

`side` は新しい版の行なら `RIGHT`（省略時）、削除された行なら `LEFT`。
範囲指定とファイル全体のコメントは扱えないため、該当範囲の先頭行への1行コメントにする。

```bash
pending-review <<'JSON'
{
  "repo": "OWNER/REPO",
  "pr": 12,
  "sha": "<40桁のSHA>",
  "add": [{"path": "src/a.go", "line": 42, "body": "[Q]\nここは〜の場合に〜になりませんか？"}],
  "reply": [{"thread": "PRRT_...", "body": "確認しました。ありがとうございます。"}],
  "update": [{"id": "PRRC_...", "body": "[nits]\n短くした文面"}]
}
JSON
```

- `add`、`reply`、`update` は省略できる。
- 追加の指摘は `add` に足す。
  同じ位置・同じ文面の保存済みコメントは重複せず、「already saved」と数えられる。
- 既存スレッドへの返信は `reply` にスレッドの GraphQL ID と本文を渡す。
  同じスレッド・同じ文面の保存済み返信は重複しない。
- 文面の短縮や修正は、出力にあるコメントIDを `update` に渡す。
  `body` は本文だけを渡し、マーカーは含めない。
- 同じコメントの追加と更新は別々に保存する。
- `add` と、マーカー付き行コメントの `update` は、指摘レベルで始まらない本文を拒否する。
- コメントの削除は扱えない。
  不要になったコメントは、ユーザーがGitHub上で消す。
- 位置が差分にないと拒否されたら、確認版のファイルと差分を読み直して位置を直す。
  直せないときだけ、ユーザーに伝える。

## 結果の扱い

| 終了コード | 意味                                       | 対応                                                                         |
| ---------: | ------------------------------------------ | ---------------------------------------------------------------------------- |
|          0 | 保存・更新できた                           | 返答へ                                                                       |
|          1 | 拒否または失敗。出力に反映済みの件数がある | 理由を伝える。通信失敗なら、同じ入力で再実行してよい（反映済みは重複しない） |
|          3 | 失敗後にサーバー側の状態を読めない         | 再実行せず、空の入力で状態を読んでから進める                                 |

保存に失敗しても、通常のコメントやほかの経路に切り替えない。
`head` が動いたときは、保存を止めてユーザーに伝える。
差分を読み直した結果、指摘の位置が変わらないと確認できた場合だけ、ユーザーの了承を得て新しいSHAで保存する。

## 返答

保存の返答は次の3点に絞る。

- 保存・更新した件数と、Pendingの状態
- 本人用の確認リンク（出力の `pending review` のURL）
- Submit reviewはGitHub上で行うこと

マーカーが公開時に本文へ残ることは、ユーザーが尋ねたときだけ伝える。
