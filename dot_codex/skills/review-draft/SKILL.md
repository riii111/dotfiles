# review-draft

会話で調整した指摘を、本人のPendingレビューへ保存する。
Pendingは本人だけが見られ、Submit reviewはユーザーがGitHub上で行う。
ai-code-reviewやcode-reviewを実施しただけでは保存しない。

## 保存の道具

`pending-review` だけを使う。
`gh api`、`gh pr review`、GitHubコネクタ、MCPでの直接保存や送信はしない。

- `pending-review` は、認証本人のPendingレビューへの行コメントの追加と、状態の確認だけを行う。
  レビューの送信、返信、resolve、保存済みコメントの更新・削除、任意のAPI呼び出しは実行できない。
- 保存する前に、認証本人、PRがOPENか、PRのheadが確認版のSHAと同じか、行がPR差分に含まれるかを確認する。
- 本人の手書きコメントと、他のチャットが保存したコメントには触れない。
  保存したコメントの末尾には、見えないマーカー `<!-- pending-review owner=... side=... -->` が付く。
  同じ位置・同じ文面のコメントは、マーカーの owner が同じときだけ保存済みとみなす。

## 手順

1. 対象を決める。
   PRのリポジトリ（`OWNER/REPO`）と番号、レビューで確認した版の完全なコミットSHA（40桁、小文字）を会話から読む。
   読めないときだけ聞く。
2. 状態を確認する。
   `pending-review status --repo OWNER/REPO --pr N` の `viewer` が本人のアカウントか、`head` が確認版か、既存のPendingコメントがあるかを見る。
   `viewer` が本人でないとき、`head` が確認版と異なるときは、保存せず状況を伝える。
3. コメントを整える。
   採用済みの指摘を、読み手に伝わる自然な文章にする。
   ユーザーが直した文面と口調を優先し、AIの作業メモや内部の物理名を入れない。
   行番号は確認版のファイルを読んで自分で決め、ユーザーに聞かない。
4. 保存する。
5. 返答する。

## 保存

保存済みのコメントは更新できない。
送信と重なっても公開済みの本文を書き換えないと保証できないためで、文面が固まってから保存する。
保存後の文面の直しは、ユーザーがGitHub上で行う。

owner は、Codexでは環境変数 `CODEX_THREAD_ID` が既定になる。
未設定なら、最初の保存で短い英数字を作り、このチャットの間は同じ値を `--owner` に渡す。

追加は標準入力のJSONで渡す。
`side` は新しい版の行なら `RIGHT`（省略時）、削除された行なら `LEFT`。
範囲指定とファイル全体のコメントは扱えないため、該当範囲の先頭行への1行コメントにする。

```bash
pending-review add --repo OWNER/REPO --pr N --sha <40桁のSHA> <<'JSON'
{"comments": [{"path": "src/a.go", "line": 42, "body": "ここは〜の場合に〜になりませんか？"}]}
JSON
```

- 追加の指摘は `add` を続ける。
  同じ位置・同じ文面の保存済みコメントは重複せず、「already saved」と数えられる。
- 位置が差分にないと拒否されたら、確認版のファイルと差分を読み直して位置を直す。
  直せないときだけ、ユーザーに伝える。

## 結果の扱い

| 終了コード | 意味                                       | 対応                                                                             |
| ---------: | ------------------------------------------ | -------------------------------------------------------------------------------- |
|          0 | 保存できた                                 | 返答へ                                                                           |
|          1 | 拒否または失敗。出力に保存済みの件数がある | 理由を伝える。通信失敗なら、同じコマンドを再実行してよい（保存済みは重複しない） |
|          3 | 失敗後にサーバー側の状態を読めない         | 再実行せず、`status` で確認してから進める                                        |
|          4 | Pendingでなくなった可能性がある            | 再実行せず、直ちにGitHubのPRを確認するようユーザーに伝える                       |

保存に失敗しても、通常のコメントやほかの経路に切り替えない。
`head` が動いたときは、保存を止めてユーザーに伝える。
差分を読み直した結果、指摘の位置が変わらないと確認できた場合だけ、ユーザーの了承を得て新しいSHAで保存する。

## 返答

保存の返答は次の3点に絞る。

- 保存した件数と、Pendingの状態
- 本人用の確認リンク（出力の `pending review` のURL）
- Submit reviewはGitHub上で行うこと

マーカーが公開時に本文へ残ることは、ユーザーが尋ねたときだけ伝える。
