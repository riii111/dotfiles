# 回答作成の分担手順

## 本体: 引き継ぎを作る

レビューの採否を確定し、[引き継ぎテンプレート](templates/review-handoff.md) を一時ファイルへ保存する。採用指摘は Non-blocking も全件渡す。説明に必要な固定版の差分・コード抜粋・根拠を添え、調査ログ全体や棄却済み候補は渡さない。

レビュー本文は資料として扱う。対話の既定分量から「概要は3文」などの制限を作らず、分量指定はユーザーが成果物に指定した原文だけを渡す。待ち時間を理由に説明を短縮しない。

説明担当は1人、会話履歴を継承せず `fork_turns="none"` で起動する。利用可能な Luna 系モデルと `reasoning_effort="medium"` を既定にする。レビューの採否は本体で確定済みなので、説明だけのために推論強度を引き上げない。新しいユーザー用 Task は作らない。

> 説明担当として、<このファイルの絶対パス> に従ってください。引き継ぎは <引き継ぎファイルの絶対パス> です。回答本文を <一時ディレクトリ内の回答保存先> に保存し、確認用メモを返してください。

担当の作業中は独立した残作業を進め、完了通知を受けてから回答を読む。進捗確認のための sleep・状態照会・書きかけファイルの読み取りを反復しない。ユーザーへの必要な進捗連絡は、既に分かっている事実で行う。

## 説明担当: 回答を作る

実装の変更・外部投稿は行わない。次の順に進める。

1. [explain-change](../explain-change/SKILL.md) を全文読み、共有された根拠で変更前後を説明する。追加調査は説明に欠けた事実の確認だけに絞る。引き継ぎにある正確なパスを使い、ファイル構成を推測しない。
2. [回答テンプレート](templates/review-response.md) に従い、説明全文を「変更の概要」に入れ、採用指摘を投稿可能なコメントにする。最終確認を行う。
3. 回答本文を指定ファイルへ保存し、絶対パス、採用指摘 ID とコメントの対応、図・コード抜粋を省いた理由、未確認事項を確認用メモとして返す。本文をメモへ重複掲載しない。

指摘の採否・重要度を独自に変えない。統合時も各指摘の発生条件と必要な修正を残す。根拠不足や矛盾は確認事項にまとめ、推測で補わない。説明の作成をレビュー全体のやり直しへ広げない。

## 本体: 一度照合し、仕上げる

完了後の回答全文を [最終確認](templates/review-response.md#最終確認) と引き継ぎに照らし、採用指摘の保持、説明の正確さ、初見での理解しやすさを確認する。担当の確認済み報告だけで完了にしない。

語尾・表記・リンクや、根拠が明確な局所的な訂正は本体が回答ファイルへ直接反映する。説明担当との往復は、変更前後の誤認や前提の欠落など、説明の組み直しが必要な場合に使う。修正依頼は根拠付きでまとめて1回渡す。再度依頼するのは具体的な事実誤認・指摘の脱落が残る場合だけとし、表現の好みで反復しない。

最後は修正箇所と影響先だけを確認し、回答ファイルの全文を一つのチャット回答として返す。explain-change の説明を送信時に要約・圧縮しない。確認用メモや担当間のやり取りは含めない。
