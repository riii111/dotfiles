# 回答作成の分担手順

## 本体: 引き継ぎを作る

レビュー結果を確定してから、次の情報を説明担当へ渡す。メッセージに収まらなければ作業用の一時ファイルを使う。

- **対象と制約**: ユーザーの依頼、PR または差分範囲、確認した head・比較元、コードを読むための絶対パスや固定版のリンク、説明に適用する言語・文体・分量の指定。
- **変更の根拠**: 目的、具体的な入力・操作と変更前後の結果、代表的な処理経路、設計理由、関連コード・テスト・仕様の場所。コードで確認した事実、資料の説明、推測を区別する。
- **採用指摘の全件**: ID、Blocking / Non-blocking とタグ、投稿先のファイル・行、発生条件、期待と実際の結果、原因、根拠、必要な修正。既存コメントと重なる場合はその関係も添える。設計・テスト整理の指摘も省かない。
- **判断に影響する補足**: 意味のある既存パターンとの差異、検証結果と未確認事項。該当するものだけ渡す。

調査ログ全体や棄却済み候補は渡さない。指摘件数をそろえるために候補を採用しない。

新しい subagent を会話履歴の継承なしで起動する。`spawn_agent` では `fork_turns="none"` を使う。起動メッセージには、このファイルと引き継ぎ資料の絶対パスを示し、「説明担当として下記の手順で回答を作る」と指定する。説明担当は新しいユーザー用 Task として作らない。

## 説明担当: 回答を作る

実装の変更・外部投稿は行わない。引き継ぎの採用指摘を使い、次の順に進める。

1. [explain-change](../explain-change/SKILL.md) を全文読み、引き継ぎの根拠と必要なコードを確認する。変更を初めて読む人向けに、単独で説明を依頼された場合と同じ説明全文を完成させる。
2. [回答テンプレート](templates/review-response.md) を読み、説明全文を「変更の概要」にそのまま入れ、採用指摘の全件を投稿可能なコメントにする。テンプレートの最終確認を行う。
3. 本体へ「回答本文」と「確認用メモ」を分けて返す。確認用メモには、採用指摘の ID と回答内コメントの対応、図・コード抜粋を省いた場合の理由、本体への確認事項だけを書く。ユーザー向けの回答本文には含めない。

指摘の採否・重要度の変更や新規追加は本体に確認する。統合する場合も各指摘の発生条件と必要な修正を残し、対応する ID を確認用メモに示す。読みやすさや分量を理由に論点を落とさない。

根拠が足りない、矛盾する、または未確認の条件がある場合は、必要な箇所を本体へ照会する。自分の推測で補って断定しない。説明の作成をレビュー全体のやり直しへ広げず、確認待ちの間は他の説明を進める。

## 本体: 回答を照合して返す

回答本文を [回答テンプレートの最終確認](templates/review-response.md#最終確認) と引き継ぎに照らして読む。説明担当の確認済みという報告だけで完了にしない。

- 採用指摘の ID と本文を突き合わせ、発生条件・影響・重要度・必要な修正が残っていることを確認する。疑義が出た指摘は根拠を再確認して採否を決め、引き継ぎを更新する。
- 初見の読者が変更前後の挙動を理解でき、必要な図と代表経路がつながっていることを確認する。コード片や図が存在するだけでは充足としない。省略が explain-change の基準に合うかも確認する。
- 不足があれば該当箇所と根拠を示して説明担当へ修正を依頼する。解消できない未確認事項は確実性を保って回答に残す。

確認後の回答本文を、一つのチャット回答として返す。本体で説明を短縮し直したり、確認用メモ・引き継ぎ資料・担当間のやり取りを回答へ加えたりしない。
