# 共通レビュー基準

人向け・AI向けで共通の調査・採否基準。回答形式は呼び出し元の SKILL に従う。

## レビュー手順

1. ユーザー指定の PR、差分範囲、比較元を優先し、指定がなければリポジトリの状態から対象差分を特定する。PR は確認した head と比較元を記録し、その版のコードを根拠にする。
2. 変更に関連する `.claude/rules`、開発・レビュー規約を、タスク資料、仕様、参考 PR とあわせて読む。
3. `memo/learnings` が存在する場合は、変更箇所やタスクに関連する資料だけを読む。現行仕様とプロジェクト固有の規約を優先する。
4. 差分だけで判断せず、必要な呼び出し元・呼び出し先、近傍実装、テスト、設定、公開 API と、層の接続部分への影響を確認する。
5. 外部仕様やバージョン依存の挙動を根拠にする場合は、対象バージョンの公式資料で確認する。
6. 差分量、影響する責務・層、独立して調査できる観点から、subagent への分担と人数を自動で決める。
7. 次の観点から具体的な指摘を出し、採否と重要度を判断する。

小さな単一目的の変更は本体で確認し、複数領域や観点にまたがる変更は subagent に分担する。ファイル数だけで増員せず、独立した担当範囲ごとに必要な人数を使う。レビューを分担する subagent は利用可能な Luna 系モデルを優先し、確認した版の差分、共通の前提、担当範囲を渡す。本体が各報告の根拠を確認し、重複を除いて統合する。分担は会話履歴を継承せず、固定版の資料・該当規約・担当範囲を渡す。共通資料は一度取得して共有し、同じ調査を各担当で繰り返さない。

質問は、答えがレビュー結果を変える場合だけ行う。分担の承認や注目点を定型質問しない。

## レビュー観点

- 正常系、エラー処理・型・伝播、異常系、境界値、リソース解放
- 関連する非同期処理、ロック、共有状態の競合、デッドロック
- 公開 API、シリアライズ形式、DB マイグレーションなどの互換性
- 採用するツールチェーンとバージョンの範囲での慣用的な設計、非推奨 API
- 命名、一貫性、性能と、近傍・類似実装から責務分割やエラー処理を変える理由
- SOLID の観点で責務と依存関係を確認し、現在の要件に不要な抽象化、重複、分岐を削れるか、より簡単な代替案があるかを検討する。原則に合わせるためだけに設計を増やさない
- 現実の失敗条件に基づかない防御処理、不要な代替処理・コード

安全性は差分に関係するものを確認する。対象は認証・認可・テナント境界、未信頼入力の解析、秘密情報、SQL・シェル・プロセス実行、ファイルパス・権限・unsafe 操作、外部通信・webhook・リダイレクト、暗号・トークン・セッション。分担時はリスクに応じて担当を割り当てる。

### テストの価値と重複

- 追加・変更テストと関連する既存テストを読み、変更後の仕様、層の接続、現実的な失敗条件を保証しているか確認する。
- 実装のコピー、モックの自己検証、型・ライブラリ保証の再確認、他テストとの重複、内部構造への過度な依存、過剰なケース分けは削除・統合の候補にする。
- 候補ごとに「削除すると、どんな現実的な不具合を見逃すか」を考え、他テストが保証する範囲も確認する。固有の保証の価値と、実行時間・不安定さ・修正負担を比較する。
- 「念のため」、テスト件数やカバレッジの維持を残す理由にしない。不足への追加提案も、見逃す不具合を具体的に示す。

## 指摘の採否と重要度

具体的な発生条件、問題になる結果、根拠、必要な変更をそろえてから採用する。未確認の条件を事実として扱わず、根拠不足の候補は取り下げるか、判断に必要な質問へ変える。

- `Blocking`: 要件違反、誤った結果、データ破損、権限漏れなど、取り込み前に修正すべき問題が根拠で確認できる
- `Non-blocking`: 取り込みを止める問題ではないが、今の差分で直す価値と具体的な改善方法がある。命名、可読性、一貫性、設計やテストの整理も含む

調査中の候補は作業メモに「論点・根拠・採用／統合／不採用と理由」を短く残す。統合時に設計・テスト整理を含む候補を照合し、重大な不具合が見つかったことだけを理由に他の観点を打ち切らない。根拠のない件数合わせはしない。

不具合が起こり得ることと、この運用で取り込みを止める必要性を分けて判断する。現在の利用段階・影響範囲・合意済みの対象外や後続対応を確認し、将来の用途のリスクだけで Blocking にしない。一方、試行段階でも目的を成立させない問題は明示する。修正案も発生条件に当てはめ、症状を解消できるか確認する。

Non-blocking は任意の改善提案として残し、未対応だけを理由に LGTM を保留しない。設計・テスト整理は具体的な保守負担や重複する保証を根拠にでき、本番障害の発生を採用の必須条件にしない。

同じ症状だけを理由に統合しない。異なる発生条件、原因、必要な修正がある場合は、それぞれが分かる形を保つ。指摘件数の上限は設けない。

## 検証

PR はレビュー対象の head に対する CI 状態を確認する。CI が緑、またはユーザーが CI で担保済みと示した場合は、重複するローカル検証を省略する。

CI の有無や成否にかかわらず、網羅的な検証を機械的に実行しない。疑わしい挙動や指摘の妥当性を確かめるために必要な最小の再現・検証だけ行う。
