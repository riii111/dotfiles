# レビュー回答テンプレート

以下の構成を使い、説明用の指示、プレースホルダー、空のセクションを完成回答に残さない。指摘がなければ変更の説明に続けて `LGTM` と記す。

```markdown
## 変更の概要

<explain-change で完成させた説明全文をそのまま挿入>

## Blocking

1. [ファイル名:行番号](検証した版の行リンク)

   > **[must] <発生条件と問題になる結果>**
   > <期待される挙動と実際の結果。必要最小限の原因。必要な修正。>

   <指摘を裏付ける仕様・実装へのリンクなど、必要な根拠>

## Non-blocking

<同じ形式で [imo]・[question]・[nits] のコメントを書く>

## 既存パターンとの差異

<意味のある差異があれば、既存の書き方、今回の差異、修正要否と理由>
```

## 変更説明の扱い

「変更の概要」には、explain-change に従って作成した説明を、図・コード抜粋・根拠へのリンクを含めてそのまま入れる。レビュー側で要約し直したり、内容を削ったりしない。事実誤認の訂正や意味を保った表記修正は行ってよい。説明の構成と分量は explain-change に委ねる。冒頭は誰が何をすると何が変わるかを示し、関数名や取得APIの列挙から始めない。代表経路を説明し、内部処理の全件解説へ広げない。「概要」という見出しを数文の要約と解釈しない。初出の仕組みや状態が何を表すか、前後の処理がどうつながるかなど、初見の読者が補わないと理解できない前提は必要な箇所で説明する。収集済みの根拠を共有し、同じ調査を繰り返さない。

## コメントを書く規則

- タイトルと冒頭は具体的な操作・入力・条件と、その結果から書く。画面操作がない変更では API の応答、保存データ、処理の完了、運用や保守の負担を示す。
- 原因は結果につながる理由が分かる範囲で説明し、関数名・型名・API 名は根拠や修正に必要なものだけ残す。最後に必要な修正を書く。方法が一意に決まらなければ満たすべき挙動を示す。
- 各コメントは全体説明を読まなくても理解できる文章にする。設計やテストの改善は具体的な修正負担や見逃す不具合から説明し、利用者への影響を作り足さない。文数は固定せず、問題になる理由を理解するための前提や因果を省いて文を詰め込まない。
- 行リンクは確認した版の対象ファイルと行に実在するものを使う。行に付けられない指摘は「PR 全体コメント」とし、架空のリンクを付けない。
- 修正が必要な既存パターンとの差異は指摘欄に置き、差異の欄で繰り返さない。
- 調査過程、確認済み箇所の網羅的な列挙、取り下げた候補、変更を求めない subagent の報告は省く。範囲の制限、未コミット変更、外部依存など、解釈を変える注意事項だけ末尾に短く添える。未実施の検証を実施済みと書かない。

本文例:

> 検索結果が2ページ以上あると、CSVには最初のページだけ出力されます。画面用の1ページ分の取得結果をそのまま出力しているためです。CSVでは検索条件に一致する全件を取得してください。

## 最終確認

変更の説明と投稿文を、explain-change の要求と本体からの引き継ぎ内容に照らして確認する。

- 採用指摘の各 ID が、重要度を保って回答のコメントに対応しているか。Non-blocking も対象にする。
- 「変更の概要」に explain-change で作成した説明全文が入り、変更前後の説明、必要な図、実装がある場合の代表経路、根拠リンクがそろっているか。
- 概要で説明した挙動がコードや指摘の成立条件と矛盾せず、意図や未実装の要件を実装済みとして説明していないか。
- 各コメントが具体的な操作・入力・発生条件と結果から始まり、全体説明なしでも問題と修正要求が分かるか。「何をする仕組みか」「なぜその結果になるか」を理解するための一言が抜け、読者に推測させていないか。
- 発生条件、影響、確実性、修正要求が落ちたり、証拠より強い断定になったりしていないか。
- 統合した指摘に、異なる原因や必要な対応の抜けがないか。

満たさない説明やコメントは書き直してから返す。
