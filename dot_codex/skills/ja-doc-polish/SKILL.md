# ja-doc-polish

指定されたファイルだけを書き直し、事実と結論は変えない。
冗長な日本語や分かりにくい表現を除き、読者が理解して判断や行動に移れる文章にする。

作業前に `../japanese-tech-writing/SKILL.md` を読む。
読者と用途に合わせて規範を使い分け、以下を優先する。
lintとfmtで直せる点は、そちらに任せる。

## 情報を選ぶ

依頼と本文から、読者と文書の用途を把握する。

- 読者の理解や判断、行動に関わらない情報を削る。
  内部仕様、自明な説明、会話の経緯は、用途に必要なものだけ残す。
- 同じ役割の説明をまとめ、網羅的な列挙は必要な場合だけ残す。
- READMEやPR説明など、判断や実行に使う文書は要点を先に示す。
  読者に必要な背景や手順も残す。

## 表現を整える

- 独立した項目は箇条書き、対応関係や比較は表にする。
  理由や因果関係は短い文章で説明する。
- 処理の流れや状態の変化、依存関係は、文章より伝わる場合にMermaidで示す。
  読者が知りたい操作や関係に絞り、本文と同じ説明を繰り返さない。
- 表の1つのセルには1つの値だけを書く。
  複数の値が入るなら、行か列に分ける。
- 項目と説明は「**語**：説明」で書く。
- 括弧書きの補足は、長さによらず必要性を見直す。
  不要なら削り、必要なら本文への統合や箇条書きへの分離を優先する。
- PRやIssueを番号だけで書かない。
  読み手に中身を読ませる例なら、タイトルとリンクを付ける。
  文書の趣旨に関わらない番号なら、その情報ごと消す。

## 全文を確認する

全文を読み直し、同じ問題が他の箇所に残っていないか確かめる。
元の文書と照合し、必要な前提や条件、手順を落としていないか確かめる。

## lintとfmt

`~/ghq/github.com/riii111/dotfiles/scripts/ai-docs` を使う。
観点と基準は同じディレクトリの `README.md` にある。

```sh
npm --prefix ~/ghq/github.com/riii111/dotfiles/scripts/ai-docs run lint -- <ファイル>
npm --prefix ~/ghq/github.com/riii111/dotfiles/scripts/ai-docs run fmt -- <ファイル>
```

lintの警告を直してからfmtをかけ、最後にもう一度lintを実行する。
警告が残るときは、残した理由を報告する。
